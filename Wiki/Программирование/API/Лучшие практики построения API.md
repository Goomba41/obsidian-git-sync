# Лучшие практики построения API по методологии REST

## Правила и советы

Было бы неплохо придерживаться правил, но не все и не всегда их можно применить, но есть правила которые стоит применять всегда и безоговорочно, чтобы всё выглядело красиво

##### 1. Kebab-case для URL

Если невозможно описать маршрут односложными выражениями, типа ```/users``` или ```/user/{:id}/avatar```, то для описания в несколько слов использовать Kebab-case

> [!error] Неправильно
> ```/systemSettings```
> ```/system_settings```

> [!success] Правильно
> ```/system-settings```

##### 2. camelCase для параметров маршрута

 > [!error] Неправильно
> ```/system-settings/{setting_id}```
> ```/system-settings/{SettingId}```

> [!success] Правильно
> ```/system-settings/{settingId}```

##### 3. Множественное число для коллекций
##### 4. URL начинается с коллекции и кончается ID

 > [!error] Неправильно
> ```/store/{storeId}/item/{itemId}/weight```
> 
> Это неправильно, потому что маршрут описывает не сам ресурс, а его свойство

> [!success] Правильно
> ```/store/{storeId}/item/{itemId}/```
> ```/store/{storeId}/```
> ```/item/{itemId}/```

##### 5. Без глаголов в URL

Если маршрут должен описывать ресурс, то в URL не стоит использовать глаголы [см. ниже](#^55063d)

> [!error] Неправильно
> ```[POST] /user/{userId}/update```
> ```[GET] /getusers```

> [!success] Правильно
> ```[PUT] /user/{userId}```

##### 6. Глаголы в URL только для операций (Non-Resource)
^55063d

В случае, запрашиваемый маршрут не должен возвращать данные, а только делает операцию, то можно использовать глаголы

> [!success] Правильно
> ```[POST] /user/{userId}/notify```

##### 7. camelCase в JSON

В случае, если в запросе есть тело (данные) или ответ от сервера в формате JSON, то имена своиств должны быть в camelCase

> [!error] Неправильно
> ```json
> {
>	user_id: 1,
>	user_name: Anton
>}
>```

> [!success] Правильно
> ```json
> {
>	userId: 1,
>	userName: Anton
>}
>```

##### 8. Мониторинг API

Я бы сказал, что это не обязательно

Службы HTTP RESTful должны реализовывать конечные точки API  ```/health```, ```/version``` и ```/metrics```, предоставляющие следующую информацию:

- ```/health``` – отвечает на запросы с кодом состояния 200 OK;
- ```/version``` – отвечает на запрос номером версии;
- ```/metrics``` – эта конечная точка будет предоставлять различные показатели, например, среднее время отклика.
    
Настоятельно рекомендуем использовать конечные точки ```/debug``` и ```/status```.

##### 10. Инструменты проектирования

##### 11. Версионирование API

Если API используется внешними сущностями, изменение конечной точки может нарушить их функциональность, поэтому использование версий обязательно. Формат версии может быть разным, как вид подписи, так и конкретная реализация.

> [!hint] Пример
> ```/api/v1/shops/{shopId}/products```

##### 12. Возвращать общее количество ресурсов в коллекции

Если API возвращает список объектов, всегда возвращать и общее количество ресурсов в ответе

> [!error] Неправильно
> ```json
> {
>	users: [
>		{userId: 1},
>		{userId: 2},
>	],
>}
>```

> [!success] Правильно
> ```json
> {
>	users: [
>		{userId: 1},
>		{userId: 2},
>	],
>	count: 2,
>}
>```

##### 13. Пагинировать ответ

При возврате коллекций должна быть возможность ограничить выводимое количество. Также это может пригодиться для фронтэнда. Пагинация также может быть реализована различными методами

> [!hint] Пример
> Параметры для реализации пагинации через ограничение и смещение
> 
> ```[GET] /users?offset=5&limit=5```

##### 14. Возвращать только необходимые поля

При возврате коллекций или ресурсов должна быть возможность ограничить выводимые поля. Это помогает снизить количество передаваемой информации для снижения нагрузки на сеть и упрощения взаимодействия с ней на фронтэнде. Формат параметров может быть реализован различными методами

> [!hint] Пример
> ```[GET] /users?fields=id,name,surname,phone```

##### 15. Передача токена через заголовок запроса

>[!question]- Размышление
>Какой либо внятной информации, почему этот способ лучше, чем через параметр строки запроса, и почему так ДОЛЖНО быть, я не нашел.
>
>В теории, под него зарезервировано место в заголовках, и он не будет съедать место в строке запроса (сам токен довольно объемный, а количество символов в строке запроса ограничено). Строка запроса предназначена для вещей, относящихся к запросу, а вещи, относящиеся в коммуникации находятся в заголовках

##### 16. Проверка Content-Type

Сервер не должен принимать **content-type**. Например, если вы принимаете **application/x-www-form-urlencoded**, злоумышленник может создать форму и запустить простой запрос POST.

> [!info]- Дополнительная информация
> Всегда валидируйте тип контента, а если хотите использовать **content-type** по умолчанию, используйте **application/json**.

##### 17. Методы HTTP для операций CRUD

Следующие методы служат для описания CRUD-функций:

-   **POST**: создание новых ресурсов и подресурсов (**C**reate).  
-   **GET**: получение представления ресурса (**R**ead).
-   **PUT**: обновление существующих ресурсов (целиком) (**U**pdate).  
-   **PATCH**: обновление существующих ресурсов, но только тех полей, которые были описаны (остальные остаются без изменений) (**U**date).  
-   **DELETE**: удаление существующих ресурсов (**D**elete).

>[!question]- Размышление
Самое неодназначное - использование **GET** или **POST** для получения представления ресурса. Может возникнуть ситуация, когда не хватает максимального количества символов в строке запроса для передачи параметра, или когда параметры должны быть переданы в особом виде, который нужно будет дополнительно парсить на бэкэнде => выгоднее использовать **POST**, но скорее всего это проблема проектирования конечных точек бэкэнда.

##### 18. Вложенные ресурсы в виде отношений

> [!hint] Пример
>- **GET /shops/2/products**: получить список всех продуктов из магазина 2.
>- **GET /shops/2/products/31**: получить подробную информацию о продукте 31, из магазина 2.
>-   **DELETE /shops/2/products/31**: удалить продукт 31 из магазина 2.
>-   **PUT /shops/2/products/31**: обновить информацию о продукте 31 (использовать только URL ресурса, а не коллекцию).  
>-   **POST /shops**: создать новый магазин и вернуть сведения о нем.

##### 19. CORS

Поддерживайте заголовки CORS (Cross-Origin Resource Sharing) для всех общедоступных API.

##### 20. HTTPS

Применяйть протокол HTTPS (зашифрованный TLS) ко всем конечным точкам, ресурсам и службам (вообще ко ВСЕМУ, что проходит через сеть).

##### 21. Обработка исключений и ошибок

Ошибки могут возникать в разных случаях, например, незапланированная ошибка кода, либо при отклонении запроса пользователя с неверными параметрами. Обычно это делается через коды HTTP, например, при серверной ошибке вовращается 5xx ошибка. Но, поскольку фронтэнд, как правило, использует эту информацию для визуального вывода, то этот подход не совсем информативен, поэтому зачастую используется ответ 200 и тело ответа с ошибкой
