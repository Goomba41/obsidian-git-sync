## Базовая информация

Любой [[API]] следует ресурсно-ориентированному дизайну и состоит из трех концепций:

- **ресурс** - часть данных (например, User)
- **коллекция** - группа ресурсов (например, []User) ^ceef4f
- **[[URL]]** или **маршрут** - местоположение ресурса или коллекции (например, /users или /user/{:id}), «имя», которое привязано к одной или нескольким конечным точкам ^e9aed5
- **конечная точка** или **эндпоинт** - программный код, скрытый за маршрутом, выполняющий возложенную на него задачу, принимающий параметры и возвращающий данные  после обработки ^46a1a5

## Правила и советы

Было бы неплохо придерживаться правил, но не все и не всегда их можно применить, но есть правила которые стоит применять всегда и безоговорочно, чтобы всё выглядело красиво

##### 1. [Kebab-case](../Общее/Типы%20регистров#Kebab-case) для [URL](#^e9aed5)

Если невозможно описать маршрут односложными выражениями, типа ```/users``` или ```/user/{:id}/avatar```, то для описания в несколько слов использовать Kebab-case

> [!error] Неправильно
> ```/systemSettings```
> ```/system_settings```

> [!success] Правильно
> ```/system-settings```

##### 2. [camelCase](../Общее/Типы%20регистров#CamelCase) для [параметров маршрута](Параметризация%20маршрутов.md#Route%20parameters%20Параметры%20маршрута)

 > [!error] Неправильно
> ```/system-settings/{setting_id}```
> ```/system-settings/{SettingId}```

> [!success] Правильно
> ```/system-settings/{settingId}```

##### 3. Множественное число для [коллекций](#^ceef4f)
##### 4. [URL](#^e9aed5) начинается с коллекции и кончается ID

 > [!error] Неправильно
> ```/store/{storeId}/item/{itemId}/weight```
> 
> Это неправильно, потому что маршрут описывает не сам ресурс, а его свойство

> [!success] Правильно
> ```/store/{storeId}/item/{itemId}/```
> ```/store/{storeId}/```
> ```/item/{itemId}/```

##### 5. Без глаголов в [URL](#^e9aed5)

Если маршрут должен описывать ресурс, то в [URL](#^e9aed5) не стоит использовать глаголы [см. ниже](#6%20Глаголы%20в%20URL%20e9aed5%20только%20для%20операций%20Non-Resource)

> [!error] Неправильно
> ```[POST] /user/{userId}/update```
> ```[GET] /getusers```

> [!success] Правильно
> ```[PUT] /user/{userId}```

##### 6. Глаголы в [URL](#^e9aed5) только для операций (Non-Resource)

В случае, запрашиваемый маршрут не должен возвращать данные, а только делает операцию, то можно использовать глаголы

> [!success] Правильно
> ```[POST] /user/{userId}/notify```

##### 7. [camelCase](../Общее/Типы%20регистров#CamelCase) в [[JSON]]

В случае, если в запросе есть тело (данные) или ответ от сервера в формате [[JSON]], то имена своиств должны быть в [camelCase](../Общее/Типы%20регистров#CamelCase)

> [!error] Неправильно
> ```json
> {
>	user_id: 1,
>	user_name: Anton
>}
>```

> [!success] Правильно
> ```json
> {
>	userId: 1,
>	userName: Anton
>}
>```

##### 8. Мониторинг [[API]]

Я бы сказал, что это не обязательно

Службы HTTP RESTful должны реализовывать конечные точки API  ```/health```, ```/version``` и ```/metrics```, предоставляющие следующую информацию:

- ```/health``` – отвечает на запросы с кодом состояния 200 OK;
- ```/version``` – отвечает на запрос номером версии;
- ```/metrics``` – эта конечная точка будет предоставлять различные показатели, например, среднее время отклика.
    
Настоятельно рекомендуем использовать конечные точки ```/debug``` и ```/status```.

##### 11. [[Версионирование]] API

Если [[API]] используется внешними сущностями, изменение [конечной точки](#^46a1a5) может нарушить их функциональность, поэтому использование версий обязательно. Формат версии может быть разным, как вид подписи, так и конкретная реализация.

> [!hint] Пример
> ```/api/v1/shops/{shopId}/products```

##### 12. Возвращать общее количество ресурсов в коллекции

Если API возвращает список объектов, всегда возвращать и общее количество ресурсов в ответе

> [!error] Неправильно
> ```json
> {
>	users: [
>		{userId: 1},
>		{userId: 2},
>	],
>}
>```

> [!success] Правильно
> ```json
> {
>	users: [
>		{userId: 1},
>		{userId: 2},
>	],
>	count: 2,
>}
>```

##### 13. [[Пагинация|Пагинировать]] ответ

При возврате коллекций должна быть возможность ограничить выводимое количество. Также это может пригодиться для фронтэнда. Пагинация также может быть реализована различными методами

> [!hint] Пример
> Параметры для реализации пагинации через ограничение и смещение
> 
> ```[GET] /users?offset=5&limit=5```

##### 14. Возвращать только необходимые поля

При возврате коллекций или ресурсов должна быть возможность ограничить выводимые поля. Это помогает снизить количество передаваемой информации для снижения нагрузки на сеть и упрощения взаимодействия с ней на фронтэнде. Формат параметров может быть реализован различными методами

> [!hint] Пример
> ```[GET] /users?fields=id,name,surname,phone```
